# 05 · 权限 · 从工具名匹配到服务器级授权

> **TL;DR**:MCP 工具在权限规则里享有一种内置 Tool 没有的写法——一条规则可以对整个 server 生效,不用给每个工具单独写一条。但反过来,MCP 工具本身完全不参与判断该不该放行这件事——它把决定权彻底交给外部规则,规则没提前说清楚,就一律先问用户。

[上一篇](04-tool-exposure.md)留了个问题:一个改名之后的 MCP 工具出现在 Tool 列表里,模型说调用就能调用吗?[Skills 系列 07 篇](../skills/07-permissions.md)已经把权限规则的基本形状讲过一遍——一条规则匹配一个工具名,决定允许、拒绝还是需要确认。这一篇不重复那套基础机制,只讲 MCP 给这套机制加了什么、又在哪里主动放弃了什么。

## 一条规则管一整个 server

普通的权限规则按工具的确切名字匹配——一条规则只对应一个工具。MCP 工具的名字[上一篇](04-tool-exposure.md)讲过,是 `mcp__server__tool` 这样的固定格式,这个格式本身给权限规则开了一个口子:**规则可以只写到 server 这一层,不写具体工具名,意思是"这个 server 底下的所有工具都按这条规则处理"**。

这不是巧合,是改名规则和权限规则配合设计出来的能力。放回[开篇](01-intro.md)那个 Jira 场景想:一个 Jira MCP server 可能声明了十几个工具——创建工单、查询状态、添加评论、关闭工单……如果每个工具都要单独写一条权限规则,装一个新 server 的使用成本会很高。有了 server 级规则,团队可以一次性表态"这个 server 整体可信,放行"或者"这个 server 整体不许用",不需要逐条列出十几个工具名。

这条能力是内置 Tool 完全没有的——Read、Bash 这些内置 Tool 没有"server"这个概念,规则永远只能精确匹配到工具本身。**MCP 工具因为名字里天然带着"归属"信息,才多出这一层规则粒度。**

## 但 MCP 工具自己什么都不判断

这是本篇最值得记住的一点,也是跟内置 Tool 反差最大的地方。

内置 Tool 里有一些是会自己做判断的——比如某个执行命令的 Tool,可能会自己识别"这条具体命令看起来安全,可以不用问",不是所有情况都无条件转交给外部规则。MCP 工具完全不是这样:**它自己那部分逻辑,不管接的是哪个 server、哪个工具,永远不会说"这次调用我看着没问题,可以直接放行"——它把这个判断百分之百让给外部的规则匹配层。**

这意味着,一个 MCP 工具最终会不会被放行,完全取决于有没有规则提前覆盖到它——覆盖到了,按规则说的办;没覆盖到,不会有任何"看起来安全所以默认放行"的兜底,而是**统一转成向用户确认**。换句话说,装一个新的 MCP server 之后,如果你没有为它写任何权限规则,它底下的每一个工具调用第一次都会弹出确认——不是因为这个工具危险,单纯是因为没有规则替它拿主意。

## 这跟 Skills 07 篇说的是同一件事的另一面

[Skills 系列 07 篇](../skills/07-permissions.md)讲过 `allowed-tools` 不会缩小 Tool 集合——没被列出的 Tool 依然可能可见、可调用,只是继续走原有的 permission policy。放到 MCP 这里,"原有的 permission policy"具体是什么样,这一篇算是把答案补全了:**没有任何工具类别享有默认的"看起来安全就放行"待遇,MCP 工具只是把这条规则体现得最彻底——它连尝试自己判断都没有,直接把决定权交出去。**

这条设计取向跟 MCP 工具的来源有关:内置 Tool 的行为是 Claude Code 自己写的代码,团队可以对"这类操作通常安全"这件事有把握;MCP 工具背后是谁在实现、实现得规不规范、会不会有意料之外的副作用,Claude Code 完全不掌握——**不敢替一个自己不了解内部逻辑的外部工具做安全判断,所以干脆不做判断,把这件事完全交给使用者自己配置的规则。**

## 下一篇预告

前几篇提到过,连接一个 server 有时候会因为"需要认证"卡住,单独归成一类不同于普通的连接失败。这个"需要认证"到底是什么状态,又是怎样从卡住变成真正连上的——中间涉及一次浏览器授权,甚至企业场景下可以做到"认证一次、所有 server 都不用再登录"。下一篇 [认证 · 从一次授权到多服务器免登录](06-authentication.md) 从这里接着讲。
