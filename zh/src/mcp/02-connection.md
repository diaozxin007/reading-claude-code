# 02 · 连接 · 从一行配置到一次握手

> **TL;DR**:一个 MCP server 要先出现在某份配置里,Claude Code 才有机会连它。配置分四层——企业下发、项目共享、用户全局、单项目私有——同名冲突时后者覆盖前者,企业配置一旦存在则独占,其余三层直接失效。连上之后不是立刻能用,要先握手确认对方还活着、支持什么能力。

[上一篇](01-intro.md)里那个 Jira server,写在哪儿才会被 Claude Code 认到?

答案不止一个地方,取决于这个 server 是谁在用。

## 同一个名字 · 四种归属

假设公司统一提供了一个连内网 Jira 的 MCP server。团队里每个人都要用,但谁的 API token 都不该出现在别人机器上——这正是 MCP server 配置要解决的第一个问题:**同一份能力,不同人用它时需要不同的私密信息,但server 本身的连法(用什么协议、连哪个地址)应该只写一遍。**

Claude Code 把配置放在四个不同的地方 · 本系列后文统一称为四种 **scope**:

- **project** ——写进项目根目录一份叫 `.mcp.json` 的文件里。这份文件可以提交到 git,团队里每个人 clone 下来都能看到"这个项目要连 Jira server",地址、启动方式写死在里面,但不含任何人的私密 token。
- **user** ——写在你自己的用户级配置里,对你打开的所有项目都生效。适合放你个人常用、跟具体项目无关的 server。
- **local** ——同样写在你自己的用户级配置里,但只对某一个具体项目生效,不会出现在你打开的其他项目中。这一层就是团队场景里"私密 token 该放的地方"——项目共享的 `.mcp.json` 只声明"这里要连 Jira",你自己的 local 配置再补上你自己的 token,两者合起来才是一份能真正连上的完整配置。
- **enterprise** ——由公司管理员统一下发,不在任何个人或项目的配置文件里,普通用户改不了。

四层之外还有两个不常提但值得记一笔的来源:命令行里临时指定的 server(只在这一次会话里生效,不写进任何配置文件),以及你在 claude.ai 网页端已经连好的连接器(会跟 Claude Code 同步)。这两个不参与下面要讲的层级合并,是独立叠加的两条线,提前说明是为了后面遇到时不至于以为矩阵漏了一类。

## 冲突时听谁的

project、user、local 三层如果都提到了同一个 server 名字,合并顺序是固定的:**local 覆盖 project 覆盖 user**。放回刚才那个团队场景里看,这个顺序不是随便定的——它保证了"团队共享的连法"始终是基线,"你自己的私密补充"永远有最后拍板权,不会出现"团队改了共享配置,结果被你本地一份很久以前的旧配置盖回去"这种反直觉的情况。

**enterprise 不参与这套合并——它是独占的。** 只要公司管理员下发的配置存在,Claude Code 只会用这份配置里列出的 server,project/user/local 三层里写的东西全部不生效。这跟"合并谁覆盖谁"是两种不同的机制:合并是同层竞争、按优先级取胜,enterprise 是直接把其他三层整体关掉。对个人用户来说,这意味着如果发现自己配置的 server 突然连不上、`/mcp` 里也看不到,先该问的问题是"公司是不是刚下发了托管配置",而不是先怀疑自己的 `.mcp.json` 写错了。

project scope 还多一道 local/user 没有的门槛:**首次使用时会弹一次确认**,把即将连接的命令、参数列出来让你过目,选择允许或拒绝。这道门槛只针对 project scope,原因不难理解——`.mcp.json` 是随项目一起被 clone 下来的,如果里面写的连接命令有问题(不管是恶意还是配置错误),你在真正运行它之前应该先看一眼,而 user/local 两层是你自己维护的配置,天然不需要这层"外部内容进来前先看一眼"的确认。

## 配置写好之后 · 还要连上、握手

配置只是"声明这里应该有一个 server",接下来才是真正建立连接。这一步 Claude Code 内部用一个五态的状态描述每个 server 此刻处在哪个阶段:**已连接、连接失败、需要认证、正在连接、已停用**。认证失败会单独归为一类而不是直接算失败,是因为处理方式完全不同——[06 篇](06-authentication.md)会展开这条路径具体怎么走;这里先记住"连不上"和"连上了但没权限"是两件事,Claude Code 把它们分得很清楚。

握手过程本身有两层等待,给的耐心程度差得很大。**建立连接**——也就是从"决定要连"到"确认对方响应了"这一步——给的时间比较短,几十秒钟内没反应就判定失败;而**一次工具调用**——连接建立好之后,模型真正发起一次调用等结果——给的时间接近没有上限。这个反差是有意为之:建立连接的过程如果都卡住,大概率是地址错了或者进程根本没起来,再等也没用;但一次工具调用的耗时完全取决于 server 那头在做什么,可能是一次很快的查询,也可能是一次要跑很久的批处理任务,提前设一个短超时反而会打断本该成功的调用。

连上之后,Claude Code 不会假设对方支持所有能力,而是先问一遍"你这边具体支持 tools、resources、prompts 里的哪几样"。这一步叫**能力协商**——双方各自申报自己支持什么,取交集,后续的每一个动作都要先看这次申报的结果:没申报支持 tools 的 server,Claude Code 根本不会去问它有哪些工具;没申报支持 resources 的,[07 篇](07-resources-elicitation.md)要讲的资源读取功能对这个 server 也不会启用。这跟 MCP 协议本身的设计取向是一致的——不要求每个 server 都实现全部能力,协商机制保证 Claude Code 只会去用对方真正声明支持的那部分。

握手成功、能力协商完成之后,server 才算真正"连上"。但连上不等于用上——connected 状态只是说这条通道现在可用,真正让模型拿到新 Tool,要看 Claude Code 用的是哪种通道跟对方说话、又怎样把对方吐出来的东西改造成一个能用的 Tool,这是接下来两篇要讲的内容。

## 下一篇预告

握手这一步默认了一件事:Claude Code 已经知道要用什么方式跟这个进程对话——是像启动一个子程序那样直接拉起来,还是像访问一个网站那样发 HTTP 请求。这个"用什么方式对话"的选择,本身就有好几种答案,而且官方协议规定的标准做法和 Claude Code 实际支持的做法之间,有一段值得单独展开的落差。下一篇 [Transport · 从子进程到远程服务](03-transport.md) 从这里继续。
