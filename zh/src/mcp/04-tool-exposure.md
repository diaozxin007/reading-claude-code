# 04 · 工具暴露 · 从 tools list 到 Tool 列表里的一条

> **TL;DR**:MCP server 说"我有一个叫 `create_issue` 的工具",Claude Code 不会直接把这个名字塞进 Tool 列表——它会先改名、包一层壳,变成模型看到的那一条。改名是为了不撞车,包壳是为了让内置 Tool 和外部 Tool 在模型眼里长一个样。

[上一篇](03-transport.md)讲完"字节怎么传过去",这一篇讲字节传过去之后发生了什么——server 申报的一个工具,怎么变成模型手里真正能调用的一个 Tool。

## 先改名 · 避免一个叫 Write 的工具捣乱

假设你连了两个 MCP server,一个叫 `jira`,一个叫 `linear`,两边都恰好有一个叫 `create_issue` 的工具。如果 Claude Code 原样把两个 `create_issue` 都塞进 Tool 列表,模型该调用哪一个?更麻烦的情况是,如果某个 server 里刚好有个工具也叫 `Write`——跟内置 Tool 撞了名——那模型调用 `Write` 的时候,到底是想读写本地文件,还是想触发那个外部工具?

Claude Code 的解法很直接:**每个从 MCP server 来的工具,名字前面都会被加上"来自哪个 server"这个前缀**,格式是 `mcp__` 加 server 名 加 `__` 加工具原名——上面的例子里,两个 `create_issue` 会变成两个不同的名字,一个属于 `jira`,一个属于 `linear`,不会撞在一起,也不会跟内置 Tool 混淆。这个改名规则本身不复杂,但它带来一个副作用值得先记下:**只看名字就能看出这个 Tool 是不是 MCP 来的、来自哪个 server**——[下一篇](05-permissions.md)要讲的"整个 server 一次性授权"这种权限语法,靠的正是这条命名规律。

改完名之后,这个工具在模型面前长什么样?**跟内置 Tool 完全一样**——同样有名字、同样有参数说明、同样出现在同一份 Tool 列表里。模型选择要不要调用它的过程,不会因为它来自外部而多问一句"这是不是 MCP 工具",这一点在[开篇](01-intro.md)已经提过,这里是它具体落地的地方。

## 参数说明直接照抄 · 不重新定义一遍

内置 Tool 的参数格式(该传什么字段、字段是什么类型)是 Claude Code 自己在代码里写死的。MCP 工具不一样——参数格式是 server 那头自己声明的,Claude Code 收到之后原样转交给模型,不会自己重新定义一套等价的描述再喂给模型。这个选择背后的道理很实际:如果 Claude Code 每接一个新 server 都要重新理解一遍它的参数结构、再翻译成自己的格式,新增一个 MCP server 的成本会高很多;直接转交,server 声明什么,模型看到的就是什么,新增一个 server 不需要 Claude Code 这一侧跟着改代码。

工具描述本身也有一个不算严的上限,超出会被截断——不是为了限制 server 表达能力,是为了避免一个描述写得过长的工具占掉过多的 Tool 列表篇幅,挤压模型判断"该用哪个工具"时的注意力。

## 一个不那么直观的选择:跳过改名

前面说改名是为了避免撞车,但 Claude Code 也留了一个反过来的口子:在某些场景下,可以让 MCP 工具**保留原名**、不加前缀,代价是它会真的覆盖掉一个同名的内置 Tool。这不是默认行为,是需要专门打开的一个选项,用在一种特定场景——SDK 场景下希望用一个自定义实现完全替换某个内置行为(比如换一套自己的文件写入逻辑代替默认的 `Write`)。即便跳过了显示名字上的改名,Claude Code 内部仍然记得这个工具"其实来自哪个 server"——[下一篇](05-permissions.md)要讲的权限判断依据的是这份内部记录,不是模型看到的那个名字,所以就算名字被跳过前缀,该有的权限规则依然生效。

## 资源类工具 · 只出现一次

MCP 工具主要处理的是[开篇](01-intro.md)提过的三类能力里的 tools,但 resources 那一类能力(server 声明的只读数据)也需要一种方式暴露给模型——不是每个 server 各自生出一套"读资源"的工具,而是**全局只有一份**"列出资源"和"读取某个资源"的通用工具,不管你连了几个支持 resources 的 server,都共用这一份。这个设计避免了"连的 server 越多,通用能力被重复注册的次数也越多"这种膨胀,[07 篇](07-resources-elicitation.md)会具体讲这两个通用工具怎么工作。

## 连接之后 · 列表不是一次性写死的

一个 server 声明的工具集合不是握手完就永远固定——它可以在运行过程中变化,比如新增了一个工具、或者下线了一个。Claude Code 会在建立连接时留意 server 有没有申报"我的工具列表可能会变",如果申报了,后续每次真的发生变化,Claude Code 会重新拉一次最新列表,替换掉这个 server 名下的旧工具,而不需要用户手动断开重连。这个机制平时不显眼,但解释了一个可能让人困惑的现象:同一次会话里,连着的某个 server 的可用工具突然多了或者少了一个,不是 bug,是对方申报的能力本身变了。

## 连接是并发的 · 结果是批量落地的

装了不止一个 MCP server 的时候,Claude Code 不会一个个顺序连——本地子进程和远程服务分别用不同的并发上限同时连,连接结果(工具、资源、通道)也不是连上一个就立刻更新一次 Tool 列表,而是攒一小段时间之后一次性批量应用。这个"攒一批再更新"的处理方式主要是工程上的效率考虑,不影响本篇要讲的道理:不管几个 server 用了多久连上、连接顺序先后如何,最终模型看到的都是同一份按固定规则命名、格式统一的 Tool 列表。

## 下一篇预告

一个改名之后的 MCP 工具出现在 Tool 列表里,不代表模型说调用就能调用——[开篇](01-intro.md)留的问题之一是"这件事该由谁批准"。上一节提到的改名规则,恰好是下一篇权限判断能够精确到"整个 server 一次性放行"的原因。下一篇 [权限 · 从工具名匹配到服务器级授权](05-permissions.md) 从这里接着讲。
