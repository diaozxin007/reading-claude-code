## 一个人忙不过来的时候

设想一个具体请求:"审查这次改动 · 顺便看看有没有性能问题 · 再核对一下文档有没有跟着改。"

一个 agent 也能做完这件事——读 diff、分析性能、检查文档,一步步串行走完。但这里面有个不舒服的地方:这三件事**互相独立**,谁也不依赖谁的结论,却被迫排成一条队,后面的等前面的。

一个自然的念头:能不能同时有几个 agent 在干活,各管一摊,互不干扰,最后再把结果合起来?

[Loop 系列](../agent-loop/00-intro.md)讲过,一个 agent 的核心是一个不断"发送完整历史 → 收响应 → 决定是否继续"的循环。这个循环本身没有"分身"的概念——它只知道自己的那份消息数组,一步步往下走。要把活派给另一个 agent,就得从这个封闭的循环里,伸出一只手去够着别的循环。

## 派一个 agent 出去,要回答四个问题

不管用哪个工具去"够着别的循环",一旦决定要派活出去,有四个问题躲不掉:

- **上下文怎么来**:对方是从零开始,还是能看到我们之前聊过的东西?是全部照搬,还是我先裁剪一遍?
- **能用什么工具**:对方手里有哪些能力?是跟我一样什么都能干,还是被限定只能读不能改?
- **以什么方式进行**:我是站在原地等它做完,还是它在后台跑、我先去做别的事?
- **做完了怎么算数**:它怎么告诉我"我做完了"——一段话就行,还是要交一份格式固定的结果?

这四个问题不是凭空列的清单——它们对应工具集里能逐字核对的四组设计。挨个看一遍。

### 上下文:新起点,还是找回旧的

`Agent` 工具的说明写得很直白:被派出去的 agent **"hasn't seen this conversation, doesn't know what you've tried"**——零继承。它唯一的信息来源是这次给的任务描述,所以这段描述必须自成一体,把"要干什么、为什么干、已经排除了哪些路子"都交代清楚,不能指望它猜。

但同一份工具说明里还留了一条后路:如果之前已经派过一个 agent 出去,想接着找它说话,可以用 `SendMessage` 指定它的名字——这次续上的不是"我"的上下文,而是**它自己**此前积累的那份历史。换句话说,"上下文怎么来"不是非此即彼的两套机制,是同一个问题的两种答案:每次都新起一个(零继承),或者找回同一个、接着它自己的历史往下说(续接)。

### 工具权限:谁能干什么

`Agent` 工具里有个 `subagent_type` 字段,决定了被派出去的 agent 手里有哪些工具。这不是随便填的自由文本,是从一份运行时枚举里选:有的类型拿到全部工具,有的被砍掉写权限(比如只读搜索型,明确不给 Edit / Write),权限边界跟着类型走。

`Workflow` 脚本里起的 agent 也是同一份注册表——可以指定跟 `Agent` 工具一样的类型,还能额外从"session 已连接的 MCP 工具"里按需取用,不是一次性全塞进去。

### 前台还是后台:等不等它

`Agent` 工具有个 `run_in_background` 字段,**默认是 true**——派出去就默认后台跑,干完了自动通知,不用在原地等。工具说明专门提醒"do NOT sleep, poll, or proactively check on its progress"——既然设计成后台默认,就不该反过来假装它是同步的。只有明确需要拿到结果才能往下走的时候,才手动切成前台。

`Workflow` 走得更彻底——整个脚本调用本身**永远是后台**,内部再有多少个 agent 同时跑,都不会让当前对话被卡住。

### 汇报:一段话,还是一份固定格式

默认情况下,一个 agent 干完活,交回来的就是**它最后说的那段话**——没有强制格式。这在活儿本身比较开放(比如"调研一下这块代码")时够用,但如果后面还要用程序去处理这份结果(比如要读里面某个字段),纯文字就不方便。

`Workflow` 里的 agent 调用多了一个选项:可以要求对方**必须**交一份符合固定结构的结果,而不是随便一段话。要不要这份"固定格式"的保证,取决于拿到结果之后是人接着读,还是代码接着处理。

## 这四个问题是同一件事的四个维度,不是四选一

回头看会发现,这四个问题彼此独立——**上下文**(新起点/续接)、**权限**(哪类工具)、**前后台**(等/不等)、**汇报**(文字/固定格式)——一次具体的"派 agent"动作,是在这四条轴上各选一个点,而不是从"几种预设套餐"里选一种。

这也是为什么"临时委托一次性任务"和"留一个常驻搭档"看似是两种不同的协作方式,拆开看其实只是**上下文**这一条轴上的两个取值,其余三条轴该怎么选跟这条轴无关。

## 规模变大之后,多出一个问题:谁去做哪份活

以上四个问题问的都是"派**一个** agent 出去"时要回答的事。但如果同时要派出去的是**一批**互相独立的活——比如十个文件各查一遍——就会冒出一个新问题,而且这个问题只有在"不止一个 agent 同时干活"时才成立:**这些活,是谁定的分工?**

这里有两种截然不同的答案:

- 一块**共享的任务板**——活儿全摆出来,谁有空谁去认领,顺序不是提前定好的。这条路径已经在 [Task 家族](../state/task-family.md)专门讲过 `owner` 认领、`blockedBy` 依赖怎么运作,这里不重复,需要细节直接读那篇。
- 一段**写死的脚本**——提前用代码规定好"这批活分几个阶段、哪个阶段要等哪个阶段",不靠临场认领,分工路径不会因为谁先手快而变。这是 `Workflow` 独有的部分,本系列会专门展开。

## 这个系列要往哪走

前四个问题各自成篇,"谁分工"这个第五问题主要展开 `Workflow` 那一半,后面再收进两个跨维度的综合问题:

- **01** 上下文——`Agent` 的零继承和 `SendMessage` 的续接,具体怎么保证"找回的是同一个人"
- **02** 工具权限——`subagent_type` 这份运行时枚举怎么运作,`Workflow` 里按需接 MCP 工具跟这个注册表是什么关系
- **03** 前台/后台——`run_in_background` 的默认反转、`Workflow` 内部的并发上限怎么定的
- **04** 汇报——纯文字 vs 固定格式结果,拿到"这活干完了"的通知具体经过哪几步;**任务管理跟结果管理是两套独立的东西**——`Task` 家族只管"谁在干、干到哪一步"这层状态,没有"输出"字段,`TaskList`/`TaskGet` 拉到的永远只是状态;真正的交付物(结果)走的是另一条独立通道(文件变化本身,或分包 agent 自己的汇报机制)。这两套各管一段、互不知道对方存在,会在这篇里展开
- **05** 谁分工——`Workflow` 脚本里的确定性编排怎么写、跟共享任务板比,牺牲了什么换来确定性(简述 Task 家族的对照 · 细节链回对应篇)
- **06** 隔离与共享的边界——几个 agent 同时跑,各自的上下文是完全隔开的吗?有没有共享的部分(比如 token 消耗算总账还是各算各的)
- **07** 收尾——回答一个更根本的问题:什么时候真的需要多 agent,什么时候只是把一件事拆得更麻烦
