## 分完工之后,谁看得见谁

上一篇讲完"活怎么分",紧接着有个问题:一批 agent 同时跑起来,他们改的东西、花的钱,是各算各的,还是共用一本账?

## 文件层面:隔离是可选的,而且有代价

`Agent` 和 `Workflow` 都提供一个 `isolation: "worktree"` 选项——开了之后,这个 agent 是在一份**独立的 git 工作副本**里改文件,不会跟同时跑的其他 agent 抢同一份文件。这不是默认行为,是要显式打开的选项,原因很直接:

> "EXPENSIVE (~200-500ms setup + disk per agent), use ONLY when agents mutate files in parallel and would otherwise conflict; the worktree is auto-removed if unchanged."

**只有当"几个 agent 会同时改文件、还真的可能冲突"这个前提成立时,才值得开**——每开一个都要花几百毫秒建一份磁盘副本,如果这个 agent 最后什么都没改,这份副本会被自动清理掉,不留痕迹。反过来说,默认不隔离——大部分时候一个 agent 只是读读文件、跑跑命令,不会跟别人冲突,没必要为每一个都单独开一份工作副本。

**隔离在文件这一层,是一个"按需购买"的工程选项,不是天然存在的边界。**

## Token 层面:从来不是各算各的

文件可以选择隔离,但 `Workflow` 脚本里的 `budget` 对象,回答的是另一件事——已经花掉多少 token。这里有一句容易被忽略但分量很重的说明:

> "the pool is shared, not per-workflow"

`budget.spent()` 统计的是**主对话加上所有正在跑的 `Workflow` 一起**花掉的输出 token——不是"这个 workflow 自己花了多少",是一整本共享账。这意味着即便文件层面用 `worktree` 把几个 agent 的改动完全隔开了,**token 消耗从设计上就没有对应的隔离选项**——不存在"这个 agent 单独算它自己的预算"这回事。

这条硬约束还带一个后果:一旦 `spent()` 达到 `total`,后续的 `agent()` 调用直接抛错。

预算是**共享的硬顶**,不是每个 agent 各自领一份配额、用完了各自的就停——是所有人一起花,谁先把这本账花到顶,后面所有人的调用都会被拦下来,不分是谁先开始跑的。

## 这个不对称说明了什么

同一个"隔离"的问题,在文件和 token 这两种资源上给出了完全不同的答案:

- **文件冲突**是一个工程问题——可以靠 `worktree` 这种机制按需解决,不需要就不用付这份代价
- **Token 花销**从来不是工程问题——它本质上是"这一轮到底要花多少钱、多少算力"的资源约束,答案从设计上就是**一本共享账**,不存在"分开算"这个选项

这个不对称不是遗漏,是设计上的立场:文件是"状态",状态可以按需切分成互不干扰的副本;token 是"消耗",消耗天然是一个累加的总量,切分成"各算各的"反而会让"这一轮到底能不能再多派一个 agent"这个问题失去意义——真正要回答的问题从来是"总共还能花多少",不是"这个 agent 自己还能花多少"。

## 这一篇留下的接口

到这里,单次派活的四个问题、批量分工的三种答案、隔离与共享的边界,都摆在桌面上了。但所有这些机制堆在一起,最终要回答一个更根本的问题:**这些机制什么时候真正值得用,什么时候只是把一件事拆得更麻烦?** 这是收尾篇要回答的。
