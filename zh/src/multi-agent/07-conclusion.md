## 六篇讲完的,是"怎么做";这一篇要问的是"该不该做"

前六篇把"多个 agent 一起协作"这件事拆成了一串具体机制——上下文怎么来、权限怎么定、前后台怎么选、汇报怎么算数、活怎么分、隔离与共享的边界在哪。这些机制堆在一起,回答的都是"如果要用多 agent,该怎么用"。但还有一个更前置的问题没碰过:**什么时候真的值得派出去,什么时候只是把一件事拆得更麻烦?**

## 先回到最初的判断:压缩比

[tools 系列 · Agent 篇](../power/agent.md)里已经给过一个具体的判断标准:

> "如果一件事的关键信息量 << 结论信息量,派 Agent。调研 100 个文件出一份 500 字报告,信息压缩比 100 倍 —— 完美 Agent 场景。改一行代码,压缩比接近 1 —— 别派 Agent,自己动手。"

这条判断是本系列六篇内容的**起点前提**,不是本系列自己的发现——但值得在收尾时重新摆到台面上,因为前六篇讨论的所有机制(零继承要付出的自成一体成本、`worktree` 隔离的几百毫秒开销、并发调度的排队等待),**全都是这个判断成立之后才有意义的**。压缩比不划算的时候,前六篇讲的一切都是白花的开销——上下文要重建、结果要核对、隔离要花时间建副本,单个 agent 直接动手反而更快。

多 agent 协作不是免费的并行加速,是用"派出去的固定成本"换"信息压缩"和"并发吞吐"——只有当省下来的比花出去的多,这笔交易才划算。

## 规模是压缩比之外的第二个理由

前六篇里,05/06 两篇讨论的"批量分工"和"隔离与共享",指向的是压缩比判断没覆盖到的另一种场景:**不是单个任务信息量大,是同时有一批彼此独立的任务**。审查十个文件、跑三种不同角度的检查、同时验证多个假设——这些任务单个拎出来看,压缩比可能并不惊人,但**放在一起串行做**,总耗时是简单加总;分给几个 agent 并发做,总耗时约等于最慢的那一个。这时候派多个 agent 争取的不是压缩,是**并发吞吐**。

这两个理由(压缩信息 / 并发吞吐)经常同时成立,但也可以只满足一个——一份信息量巨大但唯一的任务(比如整理一个巨大的历史 issue 列表),只有压缩理由,没有并发理由,派一个 agent 就够;十个各自独立的小检查,可能每个压缩比都不高,但并发理由成立,值得分给几个 agent 同时跑。

## 责任不会因为派出去而消失

不管出于哪种理由派了多少个 agent,[怎么算完成 · 从一段话到固定格式](04-completion-reporting.md)里讲过的"trust but verify"始终成立——拿回来的报告是**意图声明**,不是事实证明。规模变大之后,这条纪律不会因为"这次是十个 agent 一起交回来的"就打折扣,反而更容易被忽略:十份报告一起涌回来,核对每一份的冲动会天然被"数量本身"稀释掉。多 agent 协作解决的是**信息压缩和并发调度**,没有,也不能解决"谁来对最终结果负责"这件事——这一层责任,从派工作的人手里,从始至终没有转移出去过。

## 六个机制,收在一张表里

| 问题 | 答案 |
|---|---|
| 上下文怎么来 | `Agent` 零继承、自成一体 vs `SendMessage` 按名字续接、推送到达 |
| 权限怎么定 | `subagent_type` 预设套餐,`Agent`/`Workflow` 共用注册表 |
| 前台还是后台 | `Bash` 默认前台、`Agent` 默认后台(可反转)、`Workflow` 恒后台 |
| 怎么算完成 | 默认散文式 raw data,`Workflow` 可强制 schema;任务管理与结果管理是两套独立通道 |
| 谁去做哪份活 | 任务板运行时认领 / 脚本提前写死 / `budget` 预算驱动动态收放 |
| 隔离与共享的边界 | 文件按需隔离(`worktree`)、token 从来共享(`budget` 是一本共享账) |

## 这个系列留下的边界

开篇就交代过:这个系列没有做过正式的源码级 discovery,所有材料都来自工具 schema 本身能逐字核对的文本。这意味着六篇内容回答的是"这些工具的设计意图和外部行为是什么",而不是"这些机制内部具体怎么实现的"——后者(比如 `SendMessage` 的消息总线怎么落地、`budget` 账本的具体计量方式)如果以后有 discovery 补上,值得回来给这几篇加一层更深的印证,但不改变这六篇已经站住的结论。
