## 单派一个的问题问完了,规模一大又多一个问题

前面四篇回答的都是"派一个 agent 出去"这件事本身——上下文、权限、前后台、汇报。但如果同时有一批独立的活要分下去,会多出一个前四篇都没碰到的问题:**这些活,谁定的先后、谁定的归属?**

## 共享任务板的答案:谁先看板谁先领

`Task` 家族(`TaskCreate`/`TaskList`/`TaskGet`/`TaskUpdate`)已经在 [tools 系列 · Task 家族篇](../state/task-family.md)里讲透了完整机制——owner 认领、`blockedBy` 依赖、状态机。这里不重复展开,只点出跟"谁分工"直接相关的一条:**任务板上的分工顺序,不是提前定好的**。一份任务摆在板上,谁先看到、谁先认领,归属就落给谁——这是一种**运行时才决定**的分工方式,同一份任务清单,换一批 agent 去跑,谁领到哪个,顺序完全可能不一样。

## Workflow 的答案:脚本里写死

`Workflow` 走的是完全相反的路。脚本本身就是分工方案——`pipeline(items, stage1, stage2, ...)` 直接写明白"这一批东西依次流过哪几个阶段",`parallel(thunks)` 直接写明白"这几件事同时扔出去"。**没有"认领"这个动作**,运行时的调度器只是照着脚本执行,不替谁做归属判断。

一个具体例子说明这个差别有多彻底:同一批文件要审查,`Task` 板的做法是把每个文件建一条任务扔上板,谁有空谁认领;`Workflow` 的做法是在脚本里写 `pipeline(files, f => agent(reviewPrompt(f)))`——每个文件对应哪次 `agent()` 调用,在脚本敲下来的那一刻就已经定死了。

## 关键差异:确定性

**同一份脚本、同一份输入,`Workflow` 每次跑出来的分工路径都一样**——这是写死带来的确定性。`Task` 板则相反,分工路径依赖运行时的认领时机,同一批任务换一次运行,谁领到哪个未必相同。这不是谁更好,是两种设计在解决不同的问题:`Workflow` 追求**可重复**,`Task` 板追求**灵活加塞**——任务板允许协作过程中随时新增任务、随时调整依赖,不需要提前想清楚全局流程;`Workflow` 要求提前把整个流程想清楚才能落笔,换来的是这份流程以后可以原样重放。

## "写死"不是免费的

选 `Workflow` 这条路,前提是写脚本的人已经能预判"这批活分几个阶段、谁等谁、要不要并发"。这是一种**提前承诺**——脚本写下的那一刻,分工方案就固定了,中途想改成另一种分法,得改脚本重跑,不像任务板那样可以边做边加任务、边调整认领。

## 还有第三种答案:让预算说了算

`Workflow` 脚本里有一个 `budget` 对象,可以拿到当前这一轮设定的 token 目标,以及已经花掉多少、还剩多少。围绕这个对象,有一种既不是"写死具体几个"、也不是"认领"的分工方式——**根据剩余预算动态决定还要不要再派下一个**:

```
while (budget.total && budget.remaining() > 50_000) {
  const result = await agent("找下一批需要处理的项")
  ...
}
```

这批活最终会分给几个 agent,不是脚本作者提前写死的数字,也不是运行时几个 agent 互相抢的结果——是**跟着资源约束走**:预算宽裕就多派几轮,预算紧张就提前收手。这是"谁去做多少活"这个问题在 `Workflow` 里的第三种答案,介于"完全写死"和"完全放开抢"之间。

## 这一篇留下的接口

到这里,"谁分工"这个问题也有了三种具体答案:任务板的运行时认领、脚本的提前写死、预算驱动的动态收放。但这三种答案都还没回答一个更底层的问题:**这些同时在跑的 agent,彼此之间,哪些东西是分开的,哪些东西是共用一本账的?** ——文件改动是不是互相隔离,token 花销是不是各算各的。这是下一篇的问题。
